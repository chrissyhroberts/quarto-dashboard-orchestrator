# Quarto Dashboard Delivery System

A reusable **orchestration and delivery wrapper around ordinary Quarto projects**.

The important design principle is separation:

```text
CONTROLLER / WRAPPER                         QUARTO PROJECT
(this repository's generic machinery)       (the thing being run)

schedule / discover projects                study or business logic
optional data connectors                    data cleaning and analysis
invoke `quarto render`           ───────▶    pages, charts and tables
route operational products                  creation of product files
CSV → XLSX presentation                     interpretation of source data
Current/Archive handling                    any XLSForm-specific semantics
local / SharePoint delivery                 project-specific R/Python code
logging / hashes / cleanup
```

A new user can clone or unzip the repository, replace the two placeholder
projects with their own Quarto projects, configure `dashboard.yml`, and run the
same controller manually or on a schedule.

# Compatibility at a glance

## What Quarto projects can it run?

The wrapper is **not tied to the included examples and is not specific to an
XLSForm dashboard**.

It can orchestrate a Quarto project when:

- it lives directly under `dashboards/`
- it contains `_quarto.yml` or `_quarto.yaml`
- it contains the wrapper configuration `dashboard.yml`
- `quarto render` produces a directory that can be published

Quarto `website` and `book` projects are understood directly. Other Quarto
project types can also be used when `project.output-dir` is set explicitly.

So the practical compatibility boundary is:

> **If it is a Quarto project that renders successfully into a directory, the
> wrapper can normally treat that directory as the publication artefact.**

The wrapper does not interpret the dashboard's analytical code. The project may
use R, Python, Observable, Julia or other Quarto-supported execution engines,
provided those dependencies are installed on the machine running it.

## Built-in source connectors

The wrapper can optionally acquire data before Quarto renders:

| Source mode | Who acquires the data? | Built-in behaviour |
| --- | --- | --- |
| `none` | Nobody | No acquisition. The project uses data already present |
| `project` | Quarto project | The project acquires data itself, for example in a pre-render R or Python script |
| `kobo` | Orchestrator | Downloads a configured KoboToolbox named synchronous export as CSV or XLSX |
| `odk` | Orchestrator | Downloads ODK Central form submissions as CSV |
| `redcap` | Orchestrator | Downloads records through the REDCap API as CSV |

These connectors are conveniences. They are **not required**. A Quarto project
can obtain data from any other system itself by using `source.type: project`.

## XLSForm, Kobo and ODK: what is special?

There is **no XLSForm parser, compiler or form engine in the wrapper**.

The wrapper does not:

- read or validate an XLSForm definition
- understand survey groups, repeats, relevance or calculations
- deploy forms to KoboToolbox or ODK Central
- infer monitoring rules from a form
- convert XLSForm structure into dashboard pages

KoboToolbox and ODK Central have built-in source adapters because they are useful
places from which to retrieve submitted data. If the source form happened to be
an XLSForm, the wrapper simply receives the exported/submission data.

Anything that depends on the meaning or structure of that form belongs in the
**Quarto project**: cleaning, reshaping, repeat handling, labels, derived
variables, monitoring rules, charts and the creation of operational action
files.

That means this repository is equally usable for a Quarto dashboard whose data
has nothing to do with XLSForms.

## What can it publish or export?

There are two different output layers.

### 1. The rendered Quarto publication

The controller publishes the **entire Quarto render directory**. It does not
convert the rendered site into another format.

Typical contents are whatever Quarto produced, for example:

```text
HTML
CSS
JavaScript
images
search indexes
other assets generated by the Quarto project
```

If a Quarto project deliberately generates other files inside its render
directory, those are part of the publication too, subject to the controller's
safety checks.

### 2. Routed operational products / action files

The Quarto project's analysis can create named files outside the common rendered
dashboard and declare them as `products` in `dashboard.yml`.

The wrapper can route those files to specific target groups.

Built-in presentation handling is:

| Source product | `action_files.format: csv` | `action_files.format: xlsx` |
| --- | --- | --- |
| CSV | delivered as CSV | converted to a real XLSX workbook |
| Other file type | copied unchanged | copied unchanged |

So the special format behaviour is **CSV → XLSX**. The controller is not a
general document converter and does not convert XLSX back to CSV.

Previous target `Current/` sets can also be archived as timestamped **ZIP**
files. Controller audit output includes **JSON** summaries and **CSV** delivery
history.

## Where can it deliver?

Built-in delivery modes are:

| Mode | Destination |
| --- | --- |
| `local` | Local or mounted filesystem path |
| `sharepoint` | Microsoft SharePoint / OneDrive through an `rclone` remote |
| `both` | Both of the above |
| `none` | Render/process without delivery |

The remote implementation uses `rclone`, but the supported/documented interface
in this starter is specifically SharePoint/OneDrive. Other `rclone` backends may
be technically possible but are not claimed as tested supported destinations.

## The conceptual boundary

The cleanest way to think about the system is:

> **The orchestrator controls pipeline execution and delivery. Data acquisition
> can either be handled by the orchestrator using its built-in connectors, or
> by the Quarto project itself. The Quarto project controls transformation,
> analysis and presentation.**

### Acquisition mode A — orchestrator-managed

Use this when you want `dashboard.yml` to describe a supported upstream system.

```text
Kobo / ODK / REDCap
        ↓
   ORCHESTRATOR
   fetches data
        ↓
      QUARTO
   analyses data
        ↓
     DELIVERY
```

The orchestrator performs the API/export step before `quarto render`.

### Acquisition mode B — project-managed

Use this when the Quarto project already knows how to obtain its own data, or
when the source system is not one of the built-in connectors.

```text
   ORCHESTRATOR
        ↓
   invokes Quarto
        ↓
      QUARTO
   R / Python / etc.
        ↓
   ANY DATA SOURCE
        ↓
 analysis + render
        ↓
     DELIVERY
```

In this mode set:

```yaml
source:
  type: project
```

The orchestrator does not need to understand the upstream API. Acquisition can
happen in a Quarto pre-render step, an R or Python script, or any other project
code.

### Responsibility split

The orchestrator owns:

- project discovery and scheduling
- optional built-in source acquisition
- secrets indirection
- invoking Quarto
- publication safety checks
- routing products to target groups
- CSV-to-XLSX presentation conversion
- Current/Archive transactions
- delivery
- hashes, logs and cleanup

The Quarto project owns:

- project-managed acquisition when `source.type: project`
- project-specific data transformation
- analytical methods
- source-specific interpretation
- XLSForm semantics if applicable
- charts, tables, narrative and UI
- creation of operational product files
- any custom connectors not implemented by the orchestrator

## End-to-end model

```text
                 CHOOSE ONE ACQUISITION PATH

   A. BUILT-IN CONNECTOR             B. PROJECT-MANAGED

 Kobo / ODK / REDCap                    ORCHESTRATOR
          ↓                                  ↓
    ORCHESTRATOR                         QUARTO
      fetches data                  pre-render / R / Python
          ↓                                  ↓
        QUARTO                         ANY DATA SOURCE
          │                                  │
          └──────────────┬───────────────────┘
                         ▼
              transform / analyse / render
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
      rendered publication    declared products
              │                     │
              │               routing / XLSX
              │               Current / Archive
              └──────────┬──────────┘
                         ▼
             local filesystem or
             SharePoint / OneDrive
```

# What it does

For every configured project directly inside `dashboards/`, the controller can:

```text
acquire or prepare data
        ↓
render Quarto
        ↓
validate the rendered output
        ↓
publish the dashboard
        ↓
route target-specific action files
        ↓
archive the previous target Current/ set
        ↓
verify and log delivery
        ↓
clean declared transient files
```

The compatibility matrix above is the authoritative summary. In short: source acquisition is optional, Quarto remains responsible for analysis, and the wrapper handles rendering, routing, delivery and operational lifecycle.

# Quick start

## 1. Unzip or clone

```bash
unzip quarto-dashboard-delivery-starter.zip
cd quarto-dashboard-delivery-starter
```

If this is a new GitHub repository:

```bash
git init
git add .
git commit -m "Initial dashboard delivery system"
```

## 2. Run setup

```bash
chmod +x setup.sh dashboardctl run.sh run_all_dashboards_daily.sh
./setup.sh
```

Setup creates a persistent Python virtual environment, installs Python requirements, checks Quarto, optionally helps with `rclone`, and creates protected machine-local configuration files.

You need Python 3 and Quarto. You only need `rclone` if you want SharePoint/OneDrive delivery. Individual dashboards may have their own R or Python dependencies.

## 3. Validate the included examples

```bash
./dashboardctl validate
```

The repository ships with:

```text
dashboards/Example_Alpha/
dashboards/Example_Beta/
```

Both should validate without external services.

## 4. Run one example

On a machine with Quarto installed:

```bash
./dashboardctl test Example_Alpha
```

The delivered result appears under:

```text
dashboards/Example_Alpha/Outputs/
```

`Example_Alpha` demonstrates XLSX action files. `Example_Beta` demonstrates CSV action files and multi-project discovery.

# Adding your own dashboard

The easiest route is:

1. copy an existing Quarto project into `dashboards/My_Project/`
2. ensure it has a real Quarto output directory such as `docs`
3. add `dashboard.yml`
4. validate
5. test locally

The interactive helper can create the controller configuration:

```bash
./dashboardctl add-project
```

Or copy `dashboard.example.yml` and edit it.

A typical project is:

```text
dashboards/My_Project/
├── _quarto.yml
├── dashboard.yml
├── index.qmd
├── analysis.qmd
├── prepare_data.R
└── styles.css
```

Your `_quarto.yml` should render into a directory inside the project, for example:

```yaml
project:
  type: website
  output-dir: docs
```

Do not use the project root itself as the output directory.

# `dashboard.yml`

Each project has one controller configuration file. A representative configuration is:

```yaml
project:
  name: Example Study Dashboard

source:
  type: none

pulls: {}

delivery:
  mode: local
  local:
    root: Outputs
  archive:
    enabled: true
    current_folder: Current
    archive_folder: Archive
    timestamp_format: "%Y-%m-%dT%H%M%SZ"

dashboard:
  folder: Dashboard

action_files:
  format: xlsx

targets:
  Site_A:
    folder: Site_A
  Central_Team:
    folder: Central_Team

products:
  followup_list:
    file: exports/followup_list.csv
    targets: [Site_A, Central_Team]

  central_review:
    file: exports/central_review.csv
    targets: [Central_Team]

runtime:
  cleanup: true
  remove_after_run: []
```

## Targets and products

Targets are recipient groups or destination folders. Products are operational files created by your analysis. Routing is explicit and many-to-many.

The controller stages the complete set for each target, archives the previous `Current/` directory as a ZIP when enabled, and then replaces `Current/` only after staging succeeds.

A local delivery therefore looks like:

```text
Outputs/
├── Dashboard/
│   └── index.html ...
├── Site_A/
│   ├── Current/
│   │   └── followup_list.xlsx
│   └── Archive/
└── Central_Team/
    ├── Current/
    │   ├── followup_list.xlsx
    │   └── central_review.xlsx
    └── Archive/
```

# CSV or XLSX action files

Your analytical code may continue producing CSV internally. The recipient-facing format is controlled centrally:

```yaml
action_files:
  format: xlsx
```

Supported values are:

```text
csv
xlsx
```

CSV is the backwards-compatible controller default. The project wizard defaults to XLSX because it avoids locale-dependent delimiter handling in desktop spreadsheet software.

The XLSX writer preserves IDs and values as text, including leading zeroes. It produces a real workbook with a frozen bold header, autofilter and readable column widths. It does not merely rename a CSV file.

# Data acquisition

There are two supported acquisition models:

1. **orchestrator-managed** — use `kobo`, `odk` or `redcap`
2. **project-managed** — use `project` and let Quarto/R/Python fetch from any source

Set `source.type` to one of:

```text
none
project
kobo
odk
redcap
```

## `none`

No controller-managed acquisition. Useful for examples and dashboards using already-present data.

## `project`

The dashboard handles acquisition itself, for example in a Quarto `pre-render` R or Python script.

## KoboToolbox

The controller can download a named synchronous export. Store the API token in `config/secrets.env` and reference its environment-variable name from YAML.

## ODK Central

The controller supports bearer-token authentication or service-account email/password configuration. Keep credentials in `config/secrets.env`.

## REDCap

The controller can request CSV records through the REDCap API using a token stored outside the project YAML.

Do not put real API tokens into `dashboard.yml`.

# Secrets

`setup.sh` creates machine-local files such as:

```text
config/secrets.env
config/rclone.conf
config/runtime.env
```

They are ignored by Git. Never commit or upload them.

A secrets file uses simple `KEY=VALUE` entries, for example:

```text
EXAMPLE_KOBO_TOKEN="replace-me"
```

The YAML contains only the environment-variable name:

```yaml
source:
  type: kobo
  token_env: EXAMPLE_KOBO_TOKEN
```

# Local delivery

For the simplest installation:

```yaml
delivery:
  mode: local
  local:
    root: Outputs
```

A relative path is relative to the dashboard project. An absolute path can also be used.

# SharePoint / OneDrive delivery

SharePoint delivery uses `rclone`. Configure a remote once:

```bash
./dashboardctl sharepoint
```

Then use its name in project configuration:

```yaml
delivery:
  mode: sharepoint
  sharepoint:
    remote: research_sharepoint
    root: Dashboards/My_Project
```

Use `mode: both` to publish locally and to SharePoint.

For unattended production use, follow your organisation's service-identity, MFA, least-privilege and data-protection requirements.

# Cleanup

Cleanup is explicit:

```yaml
runtime:
  cleanup: true
  remove_after_run: []
```

After a successful run, the controller can remove controller-downloaded data, successfully delivered product files, the Quarto render directory and explicitly declared transient paths.

The configured local delivery root is protected. If a run or required product delivery fails, working files are retained for diagnosis.

Set `cleanup: false` while developing if you want to inspect generated files after each run.

# Scheduling

The easiest route is:

```bash
./dashboardctl cron
```

The scheduled command uses the persistent `.venv` and machine-local executable paths written by `setup.sh`. The controller has its own non-blocking lock so two controller runs cannot operate concurrently.

`run_all_dashboards_daily.sh` is also included as a repository-relative wrapper around `run.sh`.

---

# Logs and audit trail

The root `logs/` directory contains controller-level records such as:

```text
run_<timestamp>.log
latest_run_summary.json
delivery_history.csv
dashboard_controller.lock
```

The delivery history records destination, status, file size, row count where available and SHA-256 hash. Credentials and record contents should not be logged.

# Testing

Run the bundled tests with:

```bash
python -m pip install -r requirements.txt
python -m unittest discover -s tests -v
```

The GitHub Actions workflow runs the same unit tests on pushes and pull requests.

Before using real data, also test a complete dashboard run in your own environment, including target routing and access permissions.

Once you understand the structure you can simply remove:

```text
dashboards/Example_Alpha

```

and put your own projects directly under `dashboards/`.

The controller itself should normally remain unchanged. Study-specific code belongs in each Quarto project.

# GitHub hygiene

Before every commit:

```bash
git status
```

Check that you are not committing:

- `config/secrets.env`
- `config/rclone.conf`
- `.venv/`
- logs or locks
- generated `Outputs/`
- Quarto render directories
- real source data
- participant-level operational files

The supplied `.gitignore` covers the normal locations, but it is not a substitute for checking the commit.

# Moving to a server

You can clone the repository directly on the server and run `./setup.sh` there. That is safer than synchronising a live runtime directory with destructive file-copy commands.

If you do deploy with `rsync --delete`, **dry-run first** and protect machine-owned runtime files and directories. See `docs/MAINTAINERS.md`.

# What is not included

This starter deliberately excludes:

- deployment-specific study dashboards and analysis
- study-specific forms and site definitions
- production tokens or rclone configuration
- real study or operational data
- deployment-specific submission-archive publishers

Those components were deployment-specific and would make a public starter misleading rather than generic.

# First things to change in a new deployment

1. Rename or replace the placeholder dashboards.
2. Set each project's data source.
3. Define target groups and product routes.
4. Choose CSV or XLSX action-file delivery.
5. Configure local and/or SharePoint destination paths.
6. Put credentials only in protected machine-local configuration.
7. Run validation and tests.
8. Run manually before enabling a schedule.
9. Verify each target receives only the files it should.
10. Enable cleanup only after you are comfortable with the complete workflow.

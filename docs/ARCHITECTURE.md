# Architecture and responsibility boundary

This repository deliberately separates the **generic controller** from each
**Quarto project** it operates.

## Controller layer

Repository-level controller files include:

- `dashboard_controller.py`
- `action_file_formats.py`
- `dashboardctl`
- `run.sh`
- `run_all_dashboards_daily.sh`
- `setup.sh`

The controller can discover projects, optionally fetch data from selected
platforms, invoke Quarto, route declared product files, convert CSV products to
XLSX at the delivery boundary, archive previous target deliveries, publish to a
local filesystem or SharePoint/OneDrive, write audit records and perform safe
cleanup.

The controller is intentionally ignorant of project-specific analytical meaning.

## Quarto project layer

Each child of `dashboards/` is an ordinary Quarto project plus `dashboard.yml`.

The Quarto project owns:

- analytical and monitoring logic
- data reshaping and cleaning
- charts and tables
- user interface and narrative
- interpretation of source fields
- XLSForm-specific behaviour, if the source happens to use XLSForm
- production of any action/product files declared for routing

## Source adapters are not data models

The built-in KoboToolbox, ODK Central and REDCap connectors are transport
adapters. They retrieve data. They do not impose a survey model on the Quarto
project.

In particular, the presence of Kobo/ODK support does not make this an XLSForm
framework. There is no XLSForm parsing, validation, deployment or semantic
interpretation in the controller.

## Publication versus routed products

The rendered Quarto output directory is the common dashboard publication.

Routed products are separate named files generated by the project and assigned
to target groups in `dashboard.yml`. This separation allows a common dashboard
to be published while participant-level or operational worklists are delivered
only to authorised target folders.

CSV products may be presented to recipients as CSV or converted to XLSX. Other
product formats are copied unchanged.

## Supported built-in boundaries

### Input

- no acquisition (`none`)
- project-managed acquisition (`project`)
- KoboToolbox named exports: CSV/XLSX
- ODK Central submissions endpoint: CSV
- REDCap records API: CSV

### Quarto

Any Quarto project that can be rendered to a publication directory. Website and
book projects are detected directly. Other project types should declare
`project.output-dir`.

### Output

- rendered Quarto publication directory
- routed product files
- optional CSV-to-XLSX conversion
- ZIP archives of previous target `Current/` sets
- JSON/CSV audit records

### Delivery

- local or mounted filesystem
- SharePoint/OneDrive via `rclone`
- both
- disabled

Other source systems and destinations can be added either inside an individual
Quarto project or by implementing another controller adapter.
